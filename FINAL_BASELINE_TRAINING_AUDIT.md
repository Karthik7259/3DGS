| `--eval` | Enables the repository's every-eighth-image holdout. `readColmapSceneInfo` sorts image names and selects sorted indices 0, 8, 16, …, 248: **32 evaluation cameras and 219 training cameras**. This exact split was confirmed by preflight on the copied dataset. |

| `--save_iterations 7000 15000 30000` | Supported. Saves model PLY snapshots at the requested stages. The script also appends the final iteration to its save list; a duplicate 30,000 entry results in one save event because membership is checked per iteration. |
| `--checkpoint_iterations 7000 15000 30000` | Supported by `train.py` and `torch.save`; writes resumable `chkpnt7000.pth`, `chkpnt15000.pth`, and `chkpnt30000.pth` with captured model and optimizer state. These files can be substantially larger than PLY snapshots. |
| `--disable_viewer` | Supported flag; prevents the optional network GUI server from starting. It does not change the optimizer or renderer used for training. |

### Densification and pruning

The command does not override any densification or pruning flags. It retains official repository defaults:

- Densify from iteration 500 until before iteration 15,000.
- Densification interval: 100 iterations.
- Gradient threshold: 0.0002.
- Opacity reset interval: 3,000 iterations.
- `percent_dense`: 0.01.
- In `train.py`, `densify_and_prune` uses minimum opacity 0.005 and enables the 20-pixel size threshold after the opacity-reset interval.
- Default optimizer remains Adam.

These settings preserve the original algorithm; they also mean Gaussian count and GPU use can grow substantially before densification stops.

### VRAM and OOM risk

Using `--data_device cpu` avoids keeping all 251 RGB images and alpha masks (roughly 2 GiB at float32) resident on CUDA. The Gaussian parameters, Adam state, per-view renderer buffers, gradients, and densification intermediates still use GPU memory and depend on the evolving Gaussian count. A reasonable planning estimate is **about 4–6 GiB peak**, but this has not been measured by training. With a 6 GiB card, peak use is close to capacity and **OOM risk is material**, especially during densification or evaluation. Other GPU applications, laptop power/thermal limits, and runtime allocator fragmentation can reduce headroom.

The official Graphdeco repository lists 24 GB VRAM for paper-evaluation-quality training and says lower-memory runs may work around 8 GB; 6 GB is below that stated guidance. Their FAQ notes that changing densification settings can reduce memory but affects quality, so this audit leaves those defaults intact. [Official repository hardware requirements and FAQ](https://github.com/graphdeco-inria/gaussian-splatting#hardware-requirements)

## Duration estimate

This laptop GPU is substantially less capable, and CPU-backed image loading adds transfer overhead. ## Potential failure conditions

- **CUDA out of memory:** 6 GiB is below Graphdeco's cited low-memory guidance; densification growth and evaluation can spike memory.
- **Thermal throttling or power limits:** laptop GPU throughput can extend duration considerably.
- **Dataset copy drift:** if copied files are changed after this audit, results may not match the recorded hashes/preflight.
- **Disk growth:** checkpoints include optimizer state and may exceed expected size if Gaussian count is high.
- **Environment/import failure:** CUDA extensions passed previous smoke tests, but driver/device state or environment changes can still cause startup failures.
- **Resume behavior:** if interrupted, use a saved `chkpnt*.pth` through `--start_checkpoint` with the same model directory/config; do not overwrite or mix unrelated runs.
